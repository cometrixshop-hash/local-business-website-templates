How to Point Your Domain at a New Website (DNS in Plain English)

Published 2026-11-07 · Cometrix Web Studio guides

Getting a new website online usually ends with the same confusing step: pointing your domain name at the new host. This is DNS, and it is much less scary than it sounds. This guide explains the few records that matter, the two ways to connect a domain, and how to avoid the classic mistake of breaking your email while fixing your website.

The one idea behind DNS

A domain name is just an address that humans can read. DNS (the Domain Name System) is the phone book that translates it into the numbers and destinations computers use. When you "point a domain," you are editing a few records at your DNS provider — usually the company you bought the domain from, or whoever hosts your DNS zone.

The records you will actually touch:

RecordWhat it doesExample
APoints a name to an IPv4 addressexample.com → 185.199.108.153
AAAAPoints a name to an IPv6 addressexample.com → 2606:50c0:8000::153
CNAMEPoints a name to another namewww.example.com → you.github.io
TXTFree-form text, used for verification and email"v=spf1 ..."
MXSays where email for the domain is deliveredexample.com → mail provider

Two of these do almost all the work for a website: A (or AAAA) for the bare domain, and CNAME for the www version.

Two ways to connect

Option A: change nameservers (move all DNS to the new host)

Some hosts — Netlify, Cloudflare, many managed platforms — ask you to replace the nameservers at your registrar with theirs. After that, every record (website, email, everything) is managed in that host's dashboard.

Pros: one place to manage everything, and the host can add records automatically. Cons: if you miss a record, something else on the domain breaks — most commonly email. Before you change nameservers, write down every existing record, especially MX, TXT and any CNAME used for email or a subdomain.

Option B: keep your current DNS and add records

You can leave DNS where it is and just add the records your new host tells you. This is the lower-risk option for most small businesses, because your email records stay untouched.

Pointing at GitHub Pages

GitHub's custom domain documentation gives exact values. The steps:

  1. Add the domain in GitHub first. In your repository: Settings → Pages → Custom domain → type the domain → Save. GitHub recommends this order so nobody else can claim your subdomain.
  2. For a subdomain such as www.example.com, create a CNAME record pointing to your Pages domain: you.github.io (no repository name, no www on the target).
  3. For the bare domain example.com, create four A records pointing to GitHub's addresses:
185.199.108.153
185.199.109.153
185.199.110.153
185.199.111.153

Some DNS providers offer an ALIAS or ANAME record, which does the same job as an A record at the bare domain. If yours does, use it and point it at your Pages domain. GitHub also supports AAAA records if you want IPv6; it recommends keeping the A records too, because IPv6 adoption is still uneven.

GitHub recommends setting up both the bare domain and www. When both are configured correctly, GitHub Pages redirects one to the other automatically, so visitors reach your site either way.

Pointing at Netlify or Cloudflare Pages

These platforms typically want a CNAME for www (or an ALIAS/ANAME for the bare domain) pointing at the site's assigned hostname, such as your-site.netlify.app. Both also support connecting by nameservers. Check the platform's current custom-domain documentation for the exact target, because the assigned hostname is specific to your site.

How long it takes

DNS changes are not instant. GitHub's documentation says changes can take up to 24 hours to propagate; other providers commonly say up to 48 hours. In practice it is often a few minutes to a couple of hours. During that window some visitors see the old site and some see the new one, which is normal.

You can check progress yourself. On macOS or Linux, dig is built in:

$ dig example.com +noall +answer -t A
$ dig www.example.com +noall +answer -t CNAME

GitHub's docs use the same commands to verify configuration. If dig returns the new address, your change has taken effect for you; others may take longer.

The email trap

This is the most common way a domain move goes wrong. Email for your domain is controlled by MX records (and often TXT records for spam protection). If you delete or overwrite those while adding website records, email stops arriving — sometimes silently, with no bounce.

Rules that prevent it:

  • Never delete an MX record unless you are deliberately moving email.
  • When adding website records, add them alongside the existing ones. A, CNAME and MX records for the same name can coexist.
  • If you change nameservers, re-create every MX and TXT record from your old DNS zone before the cutover.
  • Test email right after the change: send a message to your domain address from a Gmail or Outlook account and confirm it arrives in your inbox and not in spam.
  • If you use Google Workspace or Microsoft 365, verify your setup with their admin checkup tools, which will flag missing or incorrect records.

HTTPS comes with the domain

Once the domain points at GitHub Pages, Netlify or Cloudflare Pages, HTTPS is provisioned automatically. On GitHub Pages, the "Enforce HTTPS" checkbox appears after the certificate is ready — GitHub says that can take up to 24 hours. Until it is, visitors may see a browser warning, which is exactly the problem you are trying to fix, so check it before you send anyone the new address. Checklist

  1. Write down your current MX and TXT records before touching anything.
  2. Add the custom domain in your host's settings (GitHub: repo Settings → Pages).
  3. Add the A records (bare domain) and/or CNAME (www) your host specifies.
  4. Wait, then verify with dig or the host's own check.
  5. Confirm HTTPS shows a padlock with no warning.
  6. Send a test email to your domain address and check the inbox and spam folder.
  7. Check the site on a phone over mobile data, not just your office Wi-Fi.

If anything looks wrong, you can always point the records back to where they were — DNS is reversible, it just takes time to propagate again. If you would rather have someone handle the whole move, the website refresh service includes pointing your existing domain at the new site.
